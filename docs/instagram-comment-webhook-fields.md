# Поля входящего комментария Instagram

> 2026-09-06 cursor document Instagram comment webhook fields on interactions

Документ описывает, **какие данные** из webhook комментария Instagram
сохраняются в `public.interactions`, **откуда** они берутся, **кто** их
отправляет, **зачем** они нужны и **как** ими пользоваться в n8n / backend.

Таблица `interactions` — место хранения принятого комментария. Отдельной
таблицы inbox раньше не было. `users` хранит автора (id + username), но не
сам комментарий и не публикацию.

## Как приходит событие

1. Человек пишет комментарий под постом / Reels профессионального аккаунта.
2. Meta шлёт webhook на `POST /api/webhooks/meta`.
3. Backend разбирает JSON, пишет строку в `interactions`, обновляет
   `users` / `igba_id` при необходимости и пересылает тот же JSON в n8n.
4. n8n (JavaScript2) сверяет `media.id` со списком `selected_media_ids`
   задачи автоответа.

n8n иногда оборачивает payload так: `{ "body": { "entry": [...], "object": "instagram" } }`.
Backend принимает оба варианта.

## Пример webhook

```json
{
  "object": "instagram",
  "entry": [
    {
      "id": "17841403480052658",
      "time": 1788675790,
      "changes": [
        {
          "field": "comments",
          "value": {
            "from": {
              "id": "1917627436259991",
              "username": "sveta_boltkova"
            },
            "media": {
              "id": "18143622109340491",
              "media_product_type": "REELS"
            },
            "id": "18440601349132800",
            "text": "Супер🔥"
          }
        }
      ]
    }
  ]
}
```

## Поля `interactions`

### `from_id`

- **Что:** уникальный Instagram ID человека, который оставил комментарий.
- **Откуда:** `entry.changes[].value.from.id`.
- **От кого:** от автора комментария. Это IGSID в контексте аккаунта,
  которому написали, а не `page_id` и не `graph_id` бизнеса.
- **Зачем:** однозначно узнать «кто написал», даже если username сменится.
  По этому id вызывают Graph (`is_user_follow_business`) и ищут лида в
  `users.instagram_id`.
- **Почему нельзя взять page_id / graph_id:** у бизнеса другие id
  (`17841…` / `27697…`). Messaging/comment IGSID приходит только из webhook.
- **Как писать:** backend копирует `from.id` как есть (строка цифр).

Пример: `1917627436259991` — автор `sveta_boltkova`.

### `from_username`

- **Что:** публичный никнейм автора комментария в Instagram.
- **Откуда:** `entry.changes[].value.from.username`.
- **От кого:** тот же автор, что и `from_id`.
- **Зачем:** человекочитаемое имя для логов, лидов и сверки с подключённым
  аккаунтом (`ig_accounts.username`). Если username совпал с подключённым
  аккаунтом, `from_id` можно записать в `ig_accounts.igba_id`.
- **Почему отдельно от `from_id`:** username человек может сменить, id — нет.
- **Как писать:** без `@`, в нижнем регистре (`Sveta_Boltkova` →
  `sveta_boltkova`). Дублируется в `users.username`.

### `media_id`

- **Что:** уникальный id публикации (пост / Reels / другое), под которой
  оставили комментарий.
- **Откуда:** `entry.changes[].value.media.id`.
- **От кого:** от публикации владельца бизнес-аккаунта, не от комментатора.
- **Зачем:** понять, **под каким** контентом сработал webhook. JavaScript2
  в n8n сравнивает это значение со списком `automation_tasks.selected_media_ids`.
  Если задача ограничена выбранными публикациями, комментарий под другим
  `media_id` сценарий не запускает.
- **Почему это не `comment_id`:** `media_id` — публикация, `comment_id` —
  сам комментарий. Под одним Reels может быть много комментариев.
- **Как писать:** строка из webhook без преобразований.

Пример: `18143622109340491`.

### `media_product_type`

- **Что:** формат публикации, под которой оставили комментарий.
- **Откуда:** `entry.changes[].value.media.media_product_type`.
- **От кого:** от типа контента в Instagram (Reels, обычный пост, сторис и т.д.).
- **Зачем:** отличать Reels от фото-поста и сторис. Сценарий автоответа
  может быть включён только для определённого типа контента
  (`automation_tasks.payload.content_type`, флаг `all_content_types`).
- **Почему недостаточно `media_id`:** id не говорит, Reels это или пост.
  `REELS` в примере значит: комментарий под видео Reels, не под обычное фото
  и не под сторис.
- **Как писать:** как прислала Meta (`REELS`, `FEED`, `STORY`, …).

Пример: `REELS`.

### `event_field`

- **Что:** тип изменения, на которое сработал webhook.
- **Откуда:** `entry.changes[].field`.
- **От кого:** от Meta: какая подписка сработала (комментарии, а не Direct
  и не подписка на аккаунт).
- **Зачем:** в одну таблицу и на один URL могут приходить разные события.
  `comments` означает: это комментарий. Direct приходит в `entry.messaging`,
  не в `changes`.
- **Почему фильтруем:** строка в `interactions` как комментарий пишется
  только если поле пустое или равно `comments`. `mentions` и другие field
  сюда не кладём.
- **Как писать:** копируем `field`. Для комментариев всегда `comments`.

### `event_time`

- **Что:** Unix-время события в **секундах**.
- **Откуда:** `entry.time`.
- **От кого:** от Meta, момент события на их стороне (не `created_at` нашей БД).
- **Зачем:** порядок комментариев, дедуп «кто раньше», отладка задержки
  webhook. `created_at` в таблице — когда **мы** записали строку; `event_time`
  — когда Instagram зафиксировал событие.
- **Почему секунды, не миллисекунды:** так отдаёт Meta (`1788675790`).
- **Как писать:** целое число (`BIGINT`). Не путать с JS `Date.now()`
  (миллисекунды).

Пример: `1788675790`.

### `page_id`

- **Что:** id профессиональной / бизнес-страницы Instagram, **которой**
  написали комментарий.
- **Откуда:** `entry.id`.
- **От кого:** от аккаунта-получателя (наш подключённый аккаунт), не от автора
  комментария.
- **Зачем:** понять, под каким из нескольких `ig_accounts` пришло событие.
  Сверяется с `ig_accounts.page_id` (иногда с `graph_id` / `igba_id`).
  Без этого нельзя выбрать токен, задачи и `selected_media_ids` нужного
  аккаунта.
- **Почему это не `from_id`:** `from_id` — кто написал, `page_id` — кому.
- **Как писать:** строка `entry.id` как есть.

Пример: `17841403480052658` — `page_id` аккаунта `almat.running` в примере
webhook.

### `event_object`

- **Что:** источник события на верхнем уровне webhook.
- **Откуда:** корневое поле `object` (в n8n — `body.object`).
- **От кого:** от экосистемы, которая прислала webhook.
- **Зачем:** отличить Instagram от Facebook Page. `instagram` значит:
  событие профессионального Instagram-аккаунта, не страницы Facebook.
- **Почему это не `event_field`:** `object` — продукт (`instagram`),
  `field` — вид изменения (`comments`).
- **Как писать:** копируем `object`. Для наших комментариев — `instagram`.

### `comment_id`

- **Что:** уникальный id самого комментария.
- **Откуда:** `entry.changes[].value.id`.
- **От кого:** от конкретного комментария (не автор, не публикация).
- **Зачем:** идемпотентность. Meta может прислать один webhook повторно.
  Повтор с тем же `comment_id` **обновляет** строку, а не создаёт вторую.
  Также нужен, чтобы ответить на комментарий через Graph.
- **Почему отдельно от `media_id`:** один пост — много комментариев.
- **Как писать:** уникальный индекс `idx_interactions_comment_id`.

Пример: `18440601349132800`.

### `text_content`

- **Что:** текст комментария.
- **Откуда:** `entry.changes[].value.text`.
- **От кого:** от автора комментария.
- **Зачем:** искать кодовые слова (`payload.trigger_keywords`), решать
  `exact_match`, показывать лид в интерфейсе.
- **Почему не JSON всего webhook:** для правил автоответа нужен именно текст.
- **Как писать:** как пришло, без вырезания эмодзи. Пустая строка → `NULL`.

Пример: `Супер🔥`.

### `interaction_type`

- **Что:** тип строки в CRM-таблице `interactions`.
- **Откуда:** не из webhook. Backend ставит `COMMENT`.
- **Зачем:** в enum уже есть `COMMENT`, `STORY_REPLY`, `DM`, `REELS_VIEW`.
  Комментарий из webhook помечаем как `COMMENT`, чтобы не смешать с Direct.
- **Почему enum, а не только `event_field`:** `event_field` — как назвала
  Meta; `interaction_type` — как классифицируем мы.

### `user_id`

- **Что:** внутренний UUID лида в `public.users`.
- **Откуда:** не из webhook. Backend ищет `users.instagram_id = from_id`
  после upsert автора.
- **От кого:** связь «комментарий → лид».
- **Зачем:** список лидов и история касаний без повторного поиска по
  Instagram id.
- **Почему может быть NULL:** если upsert в `users` не удался. Сам
  комментарий всё равно сохраняется с `from_id`.

### Служебные поля таблицы

| Поле | Зачем |
| --- | --- |
| `id` | UUID строки в нашей БД. Не путать с `comment_id`. |
| `created_at` | Когда backend записал строку. Не путать с `event_time`. |
| `content_id` | Старый FK на `content`. Для webhook комментария не заполняется: публикация идентифицируется `media_id`. |

## Связанные поля в других таблицах

Эти колонки **не** в `interactions`, но заполняются из того же комментария.

### `users.instagram_id`

Тот же `from.id`. Нужен, чтобы позже сравнить `sender.id` из Direct с уже
известным человеком. Уникален.

### `users.username`

Тот же `from.username`. Меняется, если человек сменил ник.

### `ig_accounts.igba_id`

Пишется **только если** `from.username` совпал с username подключённого
аккаунта и `from.id` не равен `page_id` / `graph_id`. Это messaging IGSID
самого бизнеса, когда он выступает как автор. Обычный комментатор сюда
не попадает.

## Как backend пишет строку

Файл: `backend/app/services/instagram_ids.py`, функции
`persist_messaging_ids_from_webhook` и `persist_comment_interaction`.

Вызов: `POST /api/webhooks/meta` до пересылки в n8n.

Правила:

- писать только `field=comments` (или пустой field у comment-like value);
- ключ идемпотентности — `comment_id`;
- ошибка записи не ломает HTTP 200 для Meta.

Миграция колонок: `backend/migrations/20260906_add_interactions_comment_fields.sql`.
Колонки уже применены в live-БД `mary-fitnes`.

## Как сверять публикацию в n8n

```text
webhook value.media.id
        ↓
interactions.media_id
        ↓
сравнить с automation_tasks.selected_media_ids
```

`selected_media_ids` — список Instagram media id, которые пользователь
отметил в мастере автоответа. Совпадение значит: комментарий под выбранным
Reels/постом, сценарий можно продолжать.
