# Руководство по стабилизации сервера (Ликвидация утечек памяти и 100% нагрузки CPU)

Это руководство составлено по следам инцидента, когда процесс виртуальной памяти Linux (`kswapd0`) и дублирующиеся контейнеры `n8n` полностью забили процессор (CPU) и оперативную память (RAM), вызвав зависание сервера.

---

## Часть 1. Экстренная диагностика (Когда всё зависает)

### 1. Как мгновенно увидеть виновника нагрузки

Если сервер тормозит, первая команда для проверки распределения ресурсов:

```bash
top -b -n 1 -o %CPU | head -n 20
```

- **Зачем:** Выводит топ-20 процессов, отсортированных по потреблению CPU.
- **На что смотреть:**
  - `%Cpu(s): ... sy` — если этот показатель выше 70-80%, значит процессор занят не вашим кодом, а ядро Linux пытается выжить (обычно из-за нехватки RAM).
  - `COMMAND` — имя процесса на первой строчке покажет, кто именно жрет ресурсы.
    - **`MainThr+` (n8n)** — главный процесс автоматизатора n8n. Работает на Node.js. Отвечает за логику сценариев (workflows) и вебхуки. Начинает жрать CPU, если запущен бесконечный цикл или обрабатывается огромный массив данных за раз.
    - **`uvicorn` / `python3+`** — бэкенд вашего приложения (FastAPI/Django). Отвечает за обработку HTTP-запросов и логику кода. Сильно нагружает систему при тяжелых вычислениях или при выгрузке терабайтов данных из базы (Supabase) в память за один присест.
    - **`kswapd0`** — системный процесс ядра Linux для управления виртуальной памятью. Когда физическая RAM заканчивается, он ищет, что сбросить на диск. Если подкачки (SWAP) нет, он сходит с ума, сканирует память миллиарды раз по кругу и забивает CPU на 100%.
    - **`caddy`** — веб-сервер и обратный прокси. «Входные ворота» сервера, которые раздают SSL-сертификаты (HTTPS) и перенаправляют пользователей на нужные порты контейнеров. Нагружается только при жестком наплыве трафика или DDoS-атаках.
    - **`dockerd`** — системный демон Docker. Управляет контейнерами, сетями и логами. Дает короткие всплески на CPU только в моменты команд запуска или перезапуска контейнеров.
  - `MiB Mem: ... free` — если свободного места меньше 100 МБ, сервер находится в критической зоне.
    - **`total`** — общий объем физической оперативной памяти (ОЗУ), доступный операционной системе.
    - **`free`** — абсолютно чистая, никем не занятая память, готовая к немедленному выделению под новые задачи.
    - **`used`** — объем оперативной памяти, который прямо сейчас активно потребляют все запущенные программы и контейнеры.
    - **`buff/cache`** — «умно-свободная» память. Linux временно хранит в ней часто используемые файлы с диска для ускорения системы. Как только какому-то приложению (например, n8n) резко потребуется RAM, Linux мгновенно сотрет этот кэш и отдаст память процессу.
    - **`MiB Swap` (`total / free / used`)** — показатели файла подкачки на жестком диске. Linux сгружает сюда данные «спящих» фоновых процессов, чтобы освободить дорогую физическую ОЗУ для активных задач (`n8n` и `uvicorn`).
    - **`avail Mem` (Самый важный показатель!)** — реальное количество памяти, доступное приложениям прямо сейчас без риска уронить сервер. Пока это значение держится выше 150-200 МБ, сервер в полной безопасности.

## Часть 2. Шаги по стабилизации и оптимизации

### Шаг 1. Создание и включение файла подкачки (SWAP)

**Когда применять:** Если в строке `MiB Swap` указано `0.0 total` (подкачка отключена), а физическая RAM забита на 95%+.
**Почему это важно:** Без SWAP при нехватке памяти системный процесс `kswapd0` начинает непрерывно сканировать оперативку в поисках свободных байт, сжигая 100% CPU, после чего сервер намертво засыпает. SWAP выступает «подушкой безопасности» на жестком диске.

Выполните по очереди для выделения 4 ГБ подкачки:

```bash
# 1. Создаем пустой файл размером 4 Гигабайта на диске
sudo fallocate -l 4G /swapfile

# 2. Ограничиваем права (только для root), чтобы никто не мог прочесть данные из памяти
sudo chmod 600 /swapfile

# 3. Форматируем этот файл в файловую систему подкачки
sudo mkswap /swapfile

# 4. Включаем SWAP в текущей сессии ОС
sudo swapon /swapfile

# 5. Делаем включение постоянным (чтобы подкачка не пропала после перезапуска дроплета)
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

### Шаг 2. Поиск конфигурации и удаление скрытых дубликатов контейнеров

**Зачем:** Иногда при некорректных перезапусках Docker в фоне остаются висеть старые «зомби-контейнеры» одного и того же приложения. Они не видны в стандартных логах, но продолжают выполнять старые сценарии и делить между собой оперативную память.

```bash
# 1. Находим, где на диске лежит конфигурационный файл Docker Compose
find ~ -name "docker-compose.yml" 2>/dev/null

# 2. Переходим в найденную папку проекта
cd ~/n8n-docker-caddy/

# 3. Полностью останавливаем и УНИЧТОЖАЕМ все запущенные контейнеры и их дубликаты
docker compose down

# 4. Запускаем чистые одиночные версии контейнеров в фоновом режиме
docker compose up -d
```

### Шаг 3. Жесткое ограничение аппетитов n8n (Node.js) по памяти

**Зачем и почему:** n8n написан на JavaScript (Node.js). По умолчанию среда выполнения Node.js пытается захватить столько памяти, сколько видит в системе. На сервере с 2 ГБ RAM это приводит к тому, что один тяжелый сценарий n8n выедает всю память, активируя OOM-killer (принудительное убийство процессов операционной системой).

**Как настроить:**

1. Откройте файл `docker-compose.yml` через редактор: `nano docker-compose.yml`.
2. В секцию настроек контейнера n8n (`environment:`) добавьте лимит:

```yaml
environment:
  - NODE_OPTIONS=--max-old-space-size=512
```

- **Что это делает:** Флаг `--max-old-space-size=512` жестко запрещает n8n использовать более 512 МБ оперативной памяти. Если сценарий окажется слишком тяжелым, n8n просто перезагрузит этот конкретный контейнер, но **весь остальной сервер и другие сайты продолжат работать стабильно**.

---

### Шаг 4. Настройка автоматической очистки данных (Прунинг) в n8n

**Зачем:** По умолчанию n8n сохраняет в базу данных историю выполнения каждого шага (логов) для абсолютно всех запусков. Если у вас есть сценарии, которые срабатывают раз в минуту, база данных за пару недель разрастется до гигабайтов, а n8n начнет тратить терабайты ресурсов процессора на чтение этих логов.

Добавьте эти переменные в тот же блок `environment:` файла `docker-compose.yml` для n8n:

```yaml
environment:
  - EXECUTIONS_DATA_PRUNE=true
  - EXECUTIONS_DATA_MAX_AGE=48
```

- `EXECUTIONS_DATA_PRUNE=true` — включает автоматическое удаление старой истории.
- `EXECUTIONS_DATA_MAX_AGE=48` — n8n будет хранить историю запусков только за последние 48 часов, а всё, что старше — безвозвратно и чисто удалять с диска, сохраняя быстродействие системы.

## Сводная памятка по поддержанию здоровья сервера

1. Раз в месяц заходите на сервер и проверяйте свободное место командой `df -h` (если диск забьется на 100%, Docker-контейнеры начнут падать один за другим).
2. Если в `top` процессы `uvicorn` (FastAPI) или `MainThr+` (n8n) долго удерживают нагрузку в 50-95% CPU, откройте веб-интерфейс n8n во вкладке **Executions** и найдите зависший сценарий с бесконечным циклом.
3. Отрезайте тяжелые файлы: не передавайте картинки или видео напрямую через узлы n8n, если сервер обладает скромными характеристиками (2 ГБ RAM). Используйте ссылки на файлы.
